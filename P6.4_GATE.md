## 2. Contract Summary

### 2.1 What We're Standardizing

| Area | Before | After |
|------|--------|-------|
| Response format | `{status, message}` | `{status, data, meta}` |
| Error format | `{detail: "..."}` | `{error: {code, message, message_en}}` |
| Pagination | None | `{total, limit, offset, has_more}` |
| PUT response | No data | Returns updated record |
| DELETE response | No data | Returns deleted ID |
| Request ID | None | Correlation ID in meta |

## 3. Gaps Summary

### 3.1 Critical (Must Fix)

| Gap | Impact |
|-----|--------|
| No standard response wrapper | Inconsistent client experience |
| No error codes | Can't programmatically handle errors |
| No pagination | Can't handle large datasets |
| PUT/DELETE don't return data | Client doesn't know what changed |

### 3.2 Medium (Should Fix)

| Gap | Impact |
|-----|--------|
| No request ID | Hard to debug |
| No field type validation | Invalid data possible |
| Arabic-only errors | i18n blocked |

### 3.3 Deferred (Nice to Have)

| Gap | Impact |
|-----|--------|
| No soft delete | No recovery |
| No optimistic locking | Race conditions |
| No field constraints | Less data integrity |

## 4. Breaking Changes

### 4.1 Response Format Change

**Before:**
```json
{
  "status": "success",
  "message": "تم تحديث السجل بنجاح"
}
```

**After:**
```json
{
  "status": "success",
  "data": { "id": "...", "code": "...", ... },
  "meta": { "request_id": "...", "timestamp": "...", ... }
}
```

### 4.2 Client Impact

- All clients must update to handle new format
- Error handling changes from `detail` to `error.code`
- Response parsing changes from `message` to `data`
