# EOS Design System v1.0

## Product intent
EOS is a metadata-driven ERP generation platform. The design system is therefore a product primitive, not a visual skin: generated screens must resolve metadata into the same components, states, density rules, accessibility behavior, and localization behavior.

## Official frontend direction
`erp-system/frontend` is the canonical editable frontend. `eos-system/frontend/dist` is treated as a build artifact and must not become a second source of UI truth.

## Principles
1. Clear: every screen exposes location, purpose, state, and primary action.
2. Enterprise density: support compact, comfortable, and spacious density.
3. Progressive disclosure: simple defaults, advanced controls on demand.
4. Consistent behavior: identical controls behave identically across modules.
5. Business language: technical metadata names never leak into ordinary user-facing labels.
6. Logical layout: use CSS logical properties so RTL and LTR share one implementation.
7. Accessible by default: target WCAG 2.2 AA, keyboard operation, visible focus, semantic labels, and reduced-motion support.
8. Generated by design: metadata produces UI schema, which resolves into EOS components.

## Foundations
- Primary: deep indigo (`#38578C`) with `#18233F` as the deepest brand tone.
- Neutral: slate-based scale from `#FFFFFF` to `#020617`.
- Semantic: green success, amber warning, red error, sky info.
- Typography: IBM Plex Sans + IBM Plex Sans Arabic, with Noto Sans Arabic as fallback.
- Spacing: 4px base unit.
- Default radius: 8px.
- Desktop layout: 12-column grid, responsive breakpoints, max content width 1440px.

## ERP primitives
The minimum platform component set is:

- App shell, global navigation, company switcher, notifications, command search.
- Page header, breadcrumbs, tabs, drawers, dialogs, alerts, toasts.
- Text/number/currency/date/datetime/reference inputs.
- Status badges and semantic state presentation.
- Data grid with server pagination, sorting, filtering, saved views, column visibility/reorder/resize, frozen columns, bulk actions, density, export, and keyboard navigation.
- Dynamic form renderer driven by `EosEntitySchema` and `EosFieldSchema`.
- Dashboard widgets driven by data source, permissions, role, layout, refresh policy, and filters.
- Workflow/approval timeline with state, actor, timestamp, action, and audit context.
- Empty, loading, error, permission-denied, and offline states.

## Metadata-to-UI contract

```text
Business intent
    -> metadata/entity schema
    -> UI schema
    -> component resolver
    -> EOS Design System
    -> generated ERP screen
```

The renderer must never hard-code a vendor library's component names into business metadata.

## Internationalization
All components use logical CSS properties and locale services. Dates, numbers, currencies, time zones, pluralization, and direction are presentation concerns. Persist canonical values and render them using the active locale/company/user settings.

## Quality gate
Every new UI primitive must have:
- keyboard and focus behavior
- RTL and LTR behavior
- responsive behavior
- loading/empty/error states where applicable
- accessible name/role/state
- unit/component coverage
- no hard-coded left/right spacing where logical properties apply

## Implementation order
1. Frontend authority and source-of-truth cleanup.
2. Tokens and global foundations.
3. App shell.
4. Entity workspace/data grid.
5. Metadata-driven forms.
6. Onboarding generation experience.
7. Dashboard engine.
8. Workflow/approval UX.
9. Globalization and accessibility hardening.
10. Visual regression and production QA.
