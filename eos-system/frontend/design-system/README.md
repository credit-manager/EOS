# EOS Design System v1.0

## Purpose

The EOS Design System is the visual and interaction contract for the generated ERP experience. It is intentionally independent from any single component vendor. Framework components may be used internally, but product semantics, tokens, accessibility, RTL/LTR behavior, density, and metadata rendering belong to EOS.

## Principles

1. **Clear** — every screen makes location, purpose, state, and next action obvious.
2. **Dense when useful** — ERP users can work with high information density without visual noise.
3. **Progressive** — simple defaults first; advanced controls remain discoverable.
4. **Consistent** — the same component has the same behavior across every module.
5. **Contextual** — navigation and content adapt to role, industry, permissions, and workflow.
6. **Accessible** — WCAG 2.2 AA is the baseline target; keyboard and focus behavior are first-class.
7. **Generated by design** — components must be renderable from metadata/UI schema, not hand-built per tenant.

## Architecture

```text
Business Intent
    -> Industry/Business Model
    -> Metadata
    -> UI Schema
    -> EOS Component Resolver
    -> EOS Design System
    -> Generated ERP Experience
```

## Component tiers

### Foundation

Buttons, inputs, selects, dates, currency/number fields, typography, icons, alerts, status, toast, modal, drawer, tabs, breadcrumb, search and command menu.

### ERP primitives

DataGrid, dynamic Form, record header, related-record panel, activity timeline, approval status, workflow stepper, saved view, filter builder, bulk-action bar and dashboard widget.

### Generated UI

A metadata-driven screen should specify business semantics (field type, relation, required state, visibility, order, section, permissions and workflow), while the resolver chooses the EOS component. Technical database types must never leak into the default user-facing vocabulary.

## Density

- Compact: dense accounting/inventory/procurement work.
- Comfortable: default business operations.
- Spacious: onboarding, first-run and executive dashboards.

Density is a user preference and must not change business meaning or keyboard behavior.

## RTL/LTR

Use logical CSS properties and directional semantics. Do not globally mirror every icon. Only directional icons opt into mirroring. Dates, numbers, currencies and time zones are formatted from locale/company/user settings rather than string concatenation.

## Accessibility

- Keyboard-operable controls and grids.
- Visible focus indicators.
- Semantic labels and error announcements.
- Contrast suitable for WCAG 2.2 AA.
- Reduced-motion support.
- Touch targets of at least 44px where applicable.
- Do not communicate status through color alone.

## Reference implementation order

1. App Shell / Navigation
2. Onboarding
3. Entity/Data Workspace
4. Dashboard
5. Workflow/Approval
6. Globalization and accessibility hardening

## Rule

New UI should consume tokens and EOS components. A new screen should not introduce one-off colors, spacing, typography, radii, or interaction patterns.
